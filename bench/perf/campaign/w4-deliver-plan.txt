2. zz-control-output-N threads exist only on Windows (daemon.rs #[cfg(windows)] start_control_output_tap and run_control_output_tap). On unix, terminal_requests.rs start_control_output_tap/arm_control_output_tap arm a raw output tap channel on the pane actor; EventLoop::turn calls drain_control_output_taps -> drain_output_tap -> publish_control_output_for_pane -> pump_control_output_at. Measured: a control client adds 0 threads on the Mac (p20 5 -> 5, also 5 with %output flowing).
3. Threads: Mac p1 = 2 (loop + 1 shard), p20 = 5 (loop + 4 zz-pty-shard). Linux p20 = 25 = 1 + 4 shards + 20 zz-pty-gather (pane_actor.rs PaneActor::spawn, session.rs gather_pty_linux; ZZ_PTY_GATHER=0 is the direct shard read path).
4. Frame path today: shard PaneActor::on_readable_with_spin / on_deadline -> session.rs publish_views (one Arc<TerminalViewport> per distinct live view via share_live_frame) -> Publisher::publish_frame (latest RwLock) -> notify_viewports (one coalesced ViewportReady) -> notification sink -> watchers::Sender::send(Input::Ready) + AcceptWake::wake -> loop LoopWatchers::advance -> FrameSnapshot::capture -> TerminalWatcher::handle -> per view Shared::publish_terminal_for_pane (inner lock, reconcile_copy_session, streamed kind, subscriber clone) -> TerminalViewport::diff_shared on the loop -> OutboundMailbox::enqueue_terminal_patch (encode per client: head with the global next_sequence, shared PatchTail bytes copied) -> OutboundState.terminals slot -> Connection::write_ready.
5. Fanout today: a second TUI client on a 50 Hz pane costs +6.0 Minstr per 5 s against +515 for the first (diff and patch tail already shared), so "1 encode per frame" is half done: the head, envelope and copy still run per client and full frames (NeedsFull, attach) are encoded per client.

Unwatched panes notify the loop at most every 100 ms (session.rs UNWATCHED_NOTIFY_INTERVAL, Frames::admit_notify) and every notification runs synchronize_pane_runtime with its process lookups.
8. Activity and silence: synchronize_pane_runtime per ViewportReady with output_activity (inner.last_output insert, schedule_window_silence -> timers Silence send, raise_window_activity, note_automatic_rename_output, request_peer_probe). #{pane_current_command}/#{pane_current_path} come from the PaneRuntimeFacts cache that this per-frame call fills (zz-mux formats.rs format context reads pane_runtime_facts).
9. No per-pane stream sequence barrier exists: final %output vs %exit/%window-close relies on EventLoop::turn running watchers.turn before drain_control_output_taps and on the RawOutputTapClosed token; frames carry the global Shared::next_sequence, which clients do not use for ordering (no reader in zz-client, zz-tui or clients/gpui-shared).
10. Control client: unix control_mode.rs DirectControl is already one thread (select over stdin and socket, one request per line, one 82-byte reply frame per display-message). Per command it costs 9.5 us CPU and 64 kinstr in the zz_cli process; the daemon costs 9.1 us and 66 kinstr (tmux server 11.6 us and 159 kinstr); tmux has no client cost because tmux -C hands its stdio to the server.
11. Echo per key (Mac): daemon 492 kinstr (tmux server 233), zz TUI client 105 kinstr and 70 us CPU (tmux client not measurable by rusage). Hops: zz 8 (tty to client, client to loop, loop to shard input, shard to pty and app, app to pty and shard, shard to loop, loop to client, client to tty), tmux 5 (tty to client, client to server, server to app, app to server, server to the client tty, which the server writes itself).
12. Names from the lane section at this base: watch_terminal, close_exited_terminal (now a deferred watcher effect), publish_terminal_for_pane, synchronize_pane_runtime, refresh_control_output_taps, OutboundState (daemon.rs) and EventQueueState (zz-terminal session.rs) exist as named; run_control_output_tap and the zz-control-output-N threads are Windows-only; the unix tap start moved to daemon/terminal_requests.rs Shared::start_control_output_tap; zz-pane-N threads are removed (W3-LOOP); the shard publish path is session.rs publish_views/Publisher::publish_frame called from session/pane_actor.rs and session/shard.rs; zz-pty-gather is Linux-only in PaneActor::spawn.

Risks to tmux parity:
- automatic-rename and window-renamed counts (compat/rename-timing.sh) when name checks move to a 500 ms timer; names.c arms a timer for the rest of the interval and zz must do the same.
- monitor-activity, monitor-silence and activity-based formats (window_activity, session_activity, mru ordering, choose-tree -O activity) when activity becomes an edge plus an atomic timestamp; alerts and mru-activity rows.
- #{pane_current_command}/#{pane_current_path} must be fresh at expansion (display-message right after a command starts) yet not cost a lookup per status redraw.
- copy-mode reconcile and pane-mode-changed hooks currently run inside publish_terminal_for_pane per frame; moving frames to shards must keep the hook order (pane-mode-changed before the frame that shows the mode).
- kitty images must still reach a client before the frame that places them.
- control-mode: %output pause-after ages, %continue, exit discard after EOF or a blank Return, pipe-pane -O sharing the source, one final %exit.
Risks to the per-pane stream sequence barrier:
- the sequence must be assigned where bytes are read (shard), and the loop must read the pane's current sequence when it observes an event, or an event can pass output read before it.
- a client whose terminal slot coalesces frames (latest-wins) must still count the barrier as met when a newer frame replaced the one at N.
- %output dropped by pause-after or exit discard must still release the barrier, or %exit never comes.
- pane removal and respawn reuse PaneId: the barrier must be keyed by the terminal session, not the pane id, so a respawned pane does not wait on the old sequence.
- notifications that are not about one pane (%session-changed, %layout-change for several panes) must not wait on unrelated panes.
