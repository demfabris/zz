1. P1, CONFIRMED (from the code, not reproduced): an event hook that waits panics the hook runner.
   CommandTask items have loop_wait=true (wait_queue.rs:129). When a task finishes (wait_queue.rs:261/408), run_event_hooks (daemon.rs:7698) only queues hooks to LoopHooks when loop_leaf is set (8548), and only LoopHooks sets it. So the hooks run through the synchronous runner (8569). A run-shell, if-shell or wait-for inside the hook parks (16169), advance_inserted_frames returns None, and `.expect("synchronous inserted queue finished")` (14530) panics.
   Scenario: `set-hook -g window-layout-changed 'run-shell true'`, then `split-window`. That task runs on the loop thread, which has no catch_unwind, so the daemon dies. On a worker (e.g. rename-window with a window-renamed hook), execute_work catches the panic, but the client is dropped with no response or ExecExit. Regression from the base. after-* hooks are not affected.

2. P2, CONFIRMED in code; the trigger is Linux. After a 256 KiB batch, nothing wakes the loop again for the rest of the mailbox.
   - write_ready returns after 256 KiB and calls notify_one (event_loop.rs:1788-1790), which does nothing on the loop thread (daemon.rs:2434-2438).
   - If the batch went out in full, `frames` is empty, so no WRITABLE interest is registered (event_loop.rs:1592 and after).
   - Frames and command output are now enqueued on the loop thread (the zz-pane-*/zz-output-* threads are gone), so the remainder waits for an unrelated event.
   Why Linux: a 256 KiB send buffer comes out at about 416 KiB there, so a full batch fits in one writev. A probe on this Mac took only 256 KiB of a 300 KiB write, which arms WRITABLE. ffcef23e2's Linux wake (event_loop.rs:1566-1582) only covers Control clients.
   Scenario: Linux GUI client, a window switch with large panes or kitty images queues about 600 KiB in one turn. About 300 KiB goes out; the rest waits for the next key press or timer.
