W4 ECHOMAP: where the echo latency goes, stage by stage. 2026-10-03.
Hosts: the Linux leg stopped at about 11:30 when the ssh control master to alienware expired (new logins need the owner's YubiKey). The full stage table below is measured on the Mac (M4 Max, macOS) at DL4's head perf/deliver4 970ec32ab and on the pinned tmux next-3.8; the Linux rows are the ones taken before the ssh loss. Section 7 lists what carries over and what needs the Linux leg; section 8 has the Linux commands.
Gate rows to beat (quiet alienware, 52f8e3ab): echo.p50.idle zz 1.63 ms, tmux 0.931 ms, final rule 1.5x -> zz needs 1.40 ms or less. DL4 is credited with about 64 us of it on Linux.
Evidence (scratch, not committed): /tmp/zzpc/echomap/mac/{m-probe-dl4,m-probe-tmux,m-clean-dl4,m-clean-base,m-clean-tmux,m-count-dl4,m-count-base}.json, stages-dl4-idle.json, stages-tmux-idle.json; zz probe patch /tmp/zzpc/echomap/probes-dl4-970ec32a-mac.patch (not committed). Tools committed here: w4-echomap.py (driver), w4-echomap-stages.py (stage walker), w4-echomap-sct.c / w4-echomap-sct-mac.c (LD_PRELOAD / DYLD interposer for tmux syscalls), w4-echomap-hop.c (kernel hop probe), w4-echomap-run.sh (Linux series).
Method: the driver runs echo.py's pane and key pattern (200 keys, 20-50 ms gaps, a carriage return every 25 keys, idle and busy30 sessions) through zz attach or tmux attach in a PTY, records the bench write and echo-seen instants on the probe clock (CLOCK_UPTIME_RAW on macOS, CLOCK_MONOTONIC on Linux), and samples per-process counters. zz carries temporary CLOCK_UPTIME_RAW probes (buffered, flushed by a side thread every 200 ms); tmux runs under an interposer that stamps read/readv/write/writev/recvmsg/sendmsg/select/kevent/poll. The Mac load average was 25-40 (other lanes building), so the walls are loaded-host walls; the counts are not affected.

1. The echo path, hop by hop (source, DL4 970ec32ab)
 bench write -> [W1] zz attach main thread: EventLoop::wait (kqueue on macOS, select on Linux, no timeout) -> read_terminal -> EventParser -> InteractiveClient::send_input -> ProtocolSender::send_encoded (socket write)
 -> [W2] daemon loop: EventLoop::poll_ready (mio) -> read_ready (socket read) -> dispatch -> input path (several ServerState locks, hook_events::HookScope::open and InputFocusScope::open snapshots, note_terminal_input, run_event_hooks) -> Shared::dispatch_input_key -> TerminalSession::send_key_for_view -> CommandQueues::send -> ActorWake::notify (1-byte wake-pipe write)
 -> [W3] zz-pty-shard-N: Shard::poll -> drain_wake_pipe (2 reads) -> PaneActor::on_wake (Wake::Input) -> on_command Key -> encode_key -> PtyWriter::flush_pending (pty write)
 -> kernel pty -> [W4] pane (python3 echo.py) select, read, write -> kernel pty
 -> Linux only: [W5] zz-pty-gather-N: poll_gather -> GatherPane::step (read, read to EAGAIN) -> GatherPane::send -> ActorWake::notify (wake-pipe write); macOS: the shard's kqueue sees the pty itself
 -> [W6] shard: Shard::poll (Linux: drain_wake_pipe again, on_reader_message; macOS: read_pty_buffer, read to EAGAIN) -> consume_pty_output -> publish block -> publish_active_views -> shard_sink::PaneSink -> OutboundMailbox encode() -> write_direct_terminal -> send_nonblocking (socket send)
 -> [W7] zz attach: wait -> read_protocol -> try_recv -> forward_protocol_message -> take_frames -> paint_frames -> TerminalWriter (tty write) -> bench read
 Base (pre-DL4) adds [W6b]: the frame is queued and the loop is woken through the mio Waker to write it (Connection::write_ready).
 tmux: the client hands its tty to the server and sleeps; [T1] server select/epoll -> tty read -> key table, input -> one more select for writability (libevent bufferevent writes a turn later) -> pty write; [T2] pane; [T3] server select/epoll -> pty read -> parse, redraw -> select for writability -> tty write.
 Serial wakes per echo: zz Linux 8 (W1, W2, W3, W4, W5, W6, W7, bench), zz macOS 7 (no W5), tmux 4 (T1, T2, T3, bench).

3. Wakes and syscalls per key, macOS (idle window rate subtracted; per thread from probe events inside each key's echo window)
 zz DL4: client main thread 2 wakes (stdin, frame), 1 stdin read, 1 socket write, 1 socket read, 1 tty write; process total 2.28 context switches, 6.22 unix syscalls, 81 kinstr, 56 us CPU.
  loop thread: 2.02 poll returns per key inside the echo window, one of them the key's wake (the other is not attributed), 1 socket read with data, 1 wake-pipe write.
  shard thread: 2 wakes (key, data), 2 wake-pipe reads (one drain, read to EAGAIN), 1 pty write, 2 pty reads (data, EAGAIN), 1 socket send; 0.44 more poll returns per key outside the echo windows (deadline wakes, not attributed further).
  daemon process total: 4.74 context switches, 17.06 unix syscalls, 318 kinstr, 141 us CPU (loaded host).
 zz base (perf/wave4 build 11:02): daemon 4.42 context switches, 18.02 unix syscalls (one more: the loop's frame write), 314 kinstr; client 2.11, 6.21, 77 kinstr.
 tmux: server 3.70 context switches, 11.68 unix syscalls (per key: 4 selects, 2 readv, 2 writev), 513 kinstr; client 0; pane 1.08 switches, 3.10 syscalls, 50 kinstr (same pane program under zz: 1.10, 3.10, 51).
 Linux (alienware, before the ssh loss, loaded, /proc task status and io): tmux server 3.05 wakes (idle) / 2.54 (busy30), 2.15 read-family and 2.07 write-family syscalls; client 0; pane 1.03 wakes, 1.03 reads, 1.03 writes. zz on Linux: NOT RUN (section 8). From source, zz Linux = the macOS counts plus the gather thread's 1 wake, 2 pty reads and 1 wake-pipe write, plus a second shard drain (2 more wake-pipe reads), which matches the DL4 review's 4.83 daemon wakes per key against 3 here.

4. Linux data taken before the ssh loss (alienware, not quiet: load 3-8)
 tmux echo with this driver: idle p50 0.273 ms p99 0.550, busy30 p50 0.273 p99 0.451. The quiet gate has the same tmux at 0.931: 3.4x slower when the host is idle.
 Idle states (intel_idle, menu governor, powersave, balance_performance): POLL, C1_ACPI exit 1 us, C2_ACPI exit 253 us (residency 759), C3_ACPI exit 1048 us (residency 3144). With 20-50 ms between keys the cores in the chain sit in C2/C3 when their wake arrives; a loaded host keeps them in C0/C1. On quiet alienware the echo rows measure serial wakes of sleeping threads more than instructions.
 Kernel hop probe (w4-echomap-hop.c, two threads, 400 samples, gap 2.5-7.5 ms, warm cores), write -> poll return p50/p90/p99 us: pty master->slave 26.0/37.2/72.2, pty slave->master 24.9/37.4/93.6, unix stream 16.0/24.2/42.3, pipe 12.1/20.1/46.8. The quiet idle-gap run (gap 15-45 ms) is NOT RUN; it is what prices one serial wake.

5. Ideas, tested where the Mac could test them
 Loop writes keys to the pty master itself: the hop it removes costs 20.4 us at p50 on the Mac (shard wake 5.8, command 5.0, encode and write 9.6, of which the write stays); about 15 us saved on the Mac, and on Linux one serial wake (section 6, EM2).
 Idle panes read on the shard without the gather hop: macOS already works this way and its pty write -> shard data wake step is 26.5 us against tmux's 26.4, so the shard read itself adds nothing; the Linux saving is the gather wake (EM1), Linux leg needed.
 One wake-pipe read: every drain costs 2 reads (counted: 2 per key on the Mac shard, 4 on Linux by source); a short read means the pipe is empty, so 1 read is enough; about 1 syscall per drain, CPU only (EM3).
 Shard thread affinity: nothing to gain on the Mac (Apple Silicon wakes do not pay ACPI C2/C3 exits; steps between threads are 5-6 us); on Linux it is a test of how much of the gap is idle-state exits (EM4), Linux leg needed.
 TCP_NODELAY-like options on the unix socket: none apply. AF_UNIX stream sockets have no Nagle or delayed ack, send() queues into the peer and wakes it in the same call, SO_RCVLOWAT is already 1, SO_BUSY_POLL is for NAPI network devices. Measured socket hops: 5.3 us client -> loop, 9.3 us shard -> client including the client's wake.
 Client poll timeout: the client waits with no timeout unless escape-time or writer backpressure arms a deadline; its read -> tty write step is 16.3 us of work and no timer wait was seen in 200 keys. The cost is the other way: the client sleeps about 1 ms between key and echo; on quiet Linux its wake may pay an idle exit (EM4 spin variant, Linux leg).
 Loop input path: 19.9 us p50 from socket read to dispatch_input_key on the Mac, the largest single daemon step (tmux spends about 32 us between its tty read and its next select, so this is not a gap to tmux, only the biggest piece of zz's own path). Source: the path takes the ServerState lock several times and opens HookScope and InputFocusScope snapshots before dispatching (EM5).

6. Slices (format of w4-deliver-plan.txt)
 Pricing serial wakes on quiet alienware (model until the idle-gap hop probe runs): a thread asleep since the previous echo (20-50 ms) wakes from C2/C3; one that slept a few hundred us is cheaper. DL4 removed one short-sleep wake (the loop's frame write) and measured 64 us on Linux. tmux's chain has 2 long-sleep wakes (server, pane), 1 short (server) and the bench: (0.931 - 0.273) ms over those puts a long-sleep wake at about 200-280 us. zz's chain has 5 long-sleep wakes (client, loop, shard, pane, gather).
EM1 | moves: [host: Linux; first; needs DL4 and DL5 merged (DL5 owns zz-terminal session.rs and pane_actor.rs)] an idle pane is read on its shard: Shard::poll keeps the pty fd and reads it (the ZZ_PTY_GATHER=0 path) while the pane is quiet; the gather thread only gets panes that PTY_GATHER_LEND_BUSY marks busy, through the existing lend path | removes: the gather wake W5 (a long-sleep wake), the gather's 2 pty reads become the shard's 2, one wake-pipe write and the second shard drain (2 reads) | write zone: zz-terminal session.rs PtyGather, Gather::run, GatherPane admission, PaneActor::spawn gather hand-off; session/shard.rs Shard::poll and pty_gather | risks: busy panes must still leave the shard or a 10 MB/s pane starves its shard siblings (the reason the gather exists); one fd per idle pane in the shard poll (8 per shard, SmallVec 9 holds it); buffer pool and starved flag keep one owner | done criterion: zz-pty-gather-* wakes per key 0 for an idle echo pane; quiet echo.p50.idle drops by one long-sleep wake (model 200-280 us; measure first with ZZ_PTY_GATHER=0 on DL4, which is this path for every pane); tput.* and tui-output-backpressure.sh unchanged | gate: --stage final on alienware, rows echo.*, tput.*, echo.p99.idle.p20*
EM2 | moves: [host: Mac and Linux; second; needs DL4 and DL5 merged, it edits the input path both touch] Shared::dispatch_input_key writes a plain key to the pty master on the loop thread when the actor has published a plain-input bit (no pending PtyWriter bytes, no copy mode or scrolled view, no kitty keyboard flags or modifyOtherKeys, key encodes to the same bytes in every tracked mode) on the TerminalSession; the loop queues a note for the actor without a wake (the echo wakes it) | removes: the shard key wake W3, one wake-pipe write, one drain (2 reads), the input-queue round trip; on the Mac 15 of the 20.4 us hop | write zone: daemon.rs dispatch_input_key; zz-terminal session.rs send_key_for_view and CommandQueues; pane_actor.rs on_command and encode_key (publishing the bit) | risks: ordering against bytes the actor writes (pastes, send-keys, DA/DSR replies): the fast path must check pending bytes under the PtyWriter's lock or a key overtakes a reply; echo priority (echo.open) moves to the note; a full pty must fall back to the queue; on Linux the shard's data wake becomes its first wake after a long sleep, so the net is one short-sleep wake, not a long one | done criterion: probe stages 13 -> 22 become one loop step; shard wakes per key 2 -> 1 (Mac probe count); Mac probe step loop-queued -> PTY write under 6 us; quiet Linux echo.p50.idle drops by at least 60 us (one short-sleep wake, DL4's measured size, plus the hop CPU); input-ordering tests (send-keys during paste, DSR reply interleave) pass | gate: --stage final on both hosts, rows echo.*, input.*, compat send-keys and paste rows
EM3 | moves: [host: Mac and Linux; any order] drain_wake_pipe stops after a read shorter than its 64-byte buffer (a pipe read returns what is queued, so a short read leaves it empty), or the Linux wake becomes an eventfd | removes: 1 read per drain: 1 per key on the Mac shard, 2 per key on Linux (shard twice), more on busy panes | write zone: zz-terminal session.rs drain_wake_pipe | risks: a byte written between the read and the pending-flag clear costs one extra wake, never a lost one, because the flag is cleared after the drain | done criterion: unix syscalls per key on the daemon drop by 1 on the Mac (17.06 -> 16) and by 2 on Linux; latency effect under 3 us (CPU slice) | gate: --stage final rows echo.*, cpu rows
EM4 | moves: [host: Linux; experiment before code] keep the echo chain on awake cores: pin the loop, the focused pane's shard and its gather to one core (opt-in env first), or let the attach client spin-poll for up to 2 ms after a key | removes: idle-state exits on the wake chain | write zone: zz-terminal session/shard.rs thread start, daemon.rs loop start, zz-tui event_loop.rs EventLoop::receive | risks: pinning fights the scheduler under load; a 2 ms spin per key costs about 2% of a core at 10 keys/s and tmux does not do it | done criterion: the taskset and spinner A/B in w4-echomap-run.sh (q-pin1 all on one cpu, q-pinsrv-dl4 daemon only, q-spin every core kept awake) moves quiet echo.p50.idle by more than 100 us without moving tput.* | gate: --stage final rows echo.*, tput.*, attach.*
EM5 | moves: [host: Mac and Linux; after EM2 or with it] a plain key to a terminal pane takes one ServerState lock and skips HookScope::open and InputFocusScope::open when no hook is registered for the events they watch (pane-focus, after-* and client hooks), dispatching straight to dispatch_input_key | removes: most of the 19.9 us (Mac p50) loop step between socket read and dispatch_input_key | write zone: daemon.rs input path around dispatch_input_key's callers, hook_events.rs scope openers | risks: a hook added mid-session must turn the fast path off (read the hook registry generation per key); copy-mode, display-panes and choose-tree keys keep the slow path | done criterion: Mac probe step loop socket read -> dispatch under 8 us; hook compat rows unchanged | gate: --stage final on both hosts, rows echo.*, compat hook rows
 Sum: with DL4 merged (1.63 -> about 1.57 on Linux), EM1 (one long-sleep wake, model 200-280 us) and EM2 (at least 60 us) bring the Linux row to about 1.23-1.31 ms, under 1.40; EM5 and EM3 add 10-25 us of CPU on Linux. On CPU alone the Mac-measured savings (EM2 15 us, EM5 about 12, EM3 about 1) are about 30 us and cannot reach the target: the target needs EM1's wake to be worth at least 110 us on quiet alienware, which the tmux arithmetic supports but only the Linux leg proves. If it is worth less, EM4 is the lever left, because the client wakes W1 and W7 exist only because zz attach relays the tty (tmux gives the tty to its server).

7. What carries over to Linux and what needs the Linux leg
 Carries over (same code on both): the hop structure except the gather; the relay client's cost (32.5 us of client CPU and two socket hops, Mac); the loop input step (19.9 us Mac) and the shard key hop (20.4 us Mac); the drain-to-EAGAIN double read; no client timer waits; no socket option to set; the per-thread wake and syscall counts for client, loop and shard; DL4's removal of the loop frame write (one syscall per key fewer on the Mac).
 Needs the Linux leg: anything about zz-pty-gather (W5 cost, EM1 saving, ZZ_PTY_GATHER=0 A/B); the price of one serial wake on quiet alienware (idle-gap hop probe, q-spin and q-pin runs), which decides EM1's and EM2's sizes and the whole sum; tmux's stage times under epoll on Linux; all quiet walls.
