The pin paints the prompt's trailing space inside the message-style run. zz did not.

THE CAUSE. status_overlay in crates/zz-tui/src/render.rs ran every message-area
front through text.trim_end_matches(' '). The lane added that for the overlays
fixture, where it is right, and applied it everywhere.

WHY BOTH FIXTURES ARE RIGHT. The two measure the same prompt in different grounds.

  compat/tui-overlays.sh keeps `status on`. status.c status_prompt_redraw draws the
  prompt into the status area, which already carries the message style's background,
  so tty_draw_line folds a trailing space whose background matches the row's erase
  into that erase and the cell never reaches the wire. Measured by dropping only the
  trim and re-running the fixture: exit 1, exactly 5 DIFFs, the same five the lane's
  reviewer got from the same sabotage (prompt-trailing-space, confirm-opened,
  confirm-resized, popup-under-message, popup-resized), with
    tmux: ^[[38;2;13;13;13m^[[48;2;184;134;11mOVERLAY-CONFIRM?^[[39m
    zz:   ^[[38;2;13;13;13m^[[48;2;184;134;11mOVERLAY-CONFIRM?  ^[[39m
  The pin's fill keeps the message background (only the foreground resets), which is
  what absorbs the spaces.

  compat/tui-copy-mode.sh runs with `status off` (line 424, set-option -g status off),
  and all four differing cases are in that region. With no status line the prompt is
  drawn straight onto the pane's own default ground, the space's message background
  differs from the erase background, and the pin writes the cell out: the fill after
  it resets both grounds (^[[39m^[[49m) where the confirm row resets only the
  foreground.

THE FIX (1a45ce91). status_overlay trims only when a status block sits under the
overlay: `let filled = model.status_block_rows() > 0;`. That is the same predicate
paint_status_block_in already uses to choose between painting over the status rows
and painting the single virtual row over the pane.
