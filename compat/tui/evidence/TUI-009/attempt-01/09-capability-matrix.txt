THE CAPABILITY MATRIX, declared from both sides' sources and measured where it
can be driven. The same list is the header of compat/tui-caps.sh; this copy
carries the measured values.

SOURCES READ. Pin: tmux.c (the global flag loop), tty.c (tty_start_tty, what a
client arms on attach and gives back on detach), tty-keys.c (what the terminal's
replies add to a client's feature set), tty-features.c (the feature table and
tty_add_features), tty-term.c (the capability table), input.c (what the pin
DECODES from a client, which is what makes it usable as this fixture's decoder),
format.c (the pane mode formats and format_cb_pane_key_mode),
options-table.c (extended-keys and focus-events defaults). zz:
crates/zz-tui/src/tty.rs (TerminalGuard::enter and Drop, the whole emitted set),
crates/zz-tui/src/terminal_event.rs (what zz DECODES back),
crates/zz-tui/src/render.rs (the pane-body colour path),
crates/zz/src/lib.rs (the global flag loop),
crates/zz-daemon/src/daemon.rs (client_uses_utf8, client_colour_count,
client_term_features, the client facts), crates/zz-terminal/src/model.rs
(PackedStyle).

WHY THE RECORDED EMISSION ROWS ARE WHAT THEY ARE, from source:

  wrap_flag       crates/zz-tui/src/tty.rs TerminalGuard::enter writes
                  \e[?1049h\e[?7l\e[?25l\e[?1004h. The \e[?7l is autowrap off,
                  and Drop restores \e[?7h. A full-screen renderer that
                  positions every cell explicitly needs autowrap off to write
                  the last cell of the last row without scrolling; the pin
                  keeps autowrap on and tracks that cell itself in tty.c. No
                  decoded-screen consequence: compat/tui-screen-diff.sh is
                  green at this tip, 111 asserted checkpoints identical.

  mouse_all_flag  tty.rs mouse_enable_sequence writes \e[?1003h\e[?1006h and
  mouse_button    adds \e[?1016h on a pixel-mouse terminal. \e[?1003h is
  _flag           any-event tracking, so the outer terminal reports every
                  motion for the whole attach. The pin arms \e[?1002h
                  (button-event) and raises MODE_MOUSE_ALL only while a menu is
                  up. zz's TUI does consume motion
                  (crates/zz-tui/src/input.rs menu_pointer_kind maps
                  MouseEventKind::Moved to MenuPointerKind::Motion), which is
                  what the any-event mode is for, so this is a scope difference
                  and not a bug: zz arms for the whole attach what the pin arms
                  for the life of a menu. Narrowing it means arming and
                  disarming per menu, which is app.rs, outside TUI-009's zones.

  keypad_flag     the pin sends smkx on attach (application keypad and
  keypad_cursor   application cursor keys); tty.rs sends neither. The
  _flag           consequence is confined: the outer terminal sends normal-mode
                  CSI arrows to zz, which is what
                  crates/zz-tui/src/terminal_event.rs parse_csi decodes
                  (b'A'..b'D' to Up/Down/Right/Left). zz never asks for the SS3
                  spelling, so it never has to read one.

  pane_key_mode   the pin arms extended keys through the Eneks capability,
                  which is \e[>4;2m under `extended-keys on`, and input.c
                  decodes it (INPUT_CSI_MODSET). zz ARMS NOTHING under the TERM
                  this case drives, and the decoder records VT10x.
                  CORRECTED AT THE GATE 2026-09-10. The first record said zz
                  arms the Kitty protocol \e[>3u and the pin's CSI table
                  ignores it. That is false for the case that measured this.
                  tty.rs writes \e[>3u only when guard.kitty_keyboard is set,
                  and supports_kitty_keyboard reads TERM/TERM_PROGRAM for
                  ghostty, kitty, wezterm, foot or zz; this fixture attaches
                  with TERM=xterm-256color, which matches none of them, so no
                  extended-key request is written at all. Measured by capturing
                  the attach stream against a throwaway daemon built from this
                  tip: 0 occurrences of \e[>3u under TERM=xterm-256color, 1
                  under TERM=xterm-ghostty; \e[?1004h present under both, which
                  is the focus claim confirmed.
                  The 'pin's CSI dispatch table has exactly one u entry,
                  { 'u', "", INPUT_CSI_RCP }, with NO intermediate' reading is
                  still true of the pin, but it describes what WOULD happen on
                  a kitty-class TERM, which this fixture does not drive. It is
                  a source read about an untested configuration, not the
                  mechanism behind the measurement above.
                  EITHER WAY THE MEASUREMENT STANDS: attached to a tmux-class
                  outer terminal zz gets no extended keys where the pin gets
                  Ext 2. Meeting the pin means
                  also arming modifyOtherKeys, and decoding the
                  \e[27;<mod>;<key>~ form it produces, which
                  terminal_event.rs does not do today - it decodes only the
                  Kitty \e[<key>;<mod>u form (parse_kitty_key). That decoder is
                  not in TUI-009's zone list, so it is named here rather than
                  changed.
